# DEVLOG 2026-05-27

## Phase 3c — 生产环境说话人分离链路的首次语义阅读

数据来源：`runs/20260526T051055_replay_s600/` — `tests/test.mp3` 前 600s
以 4× 速率回放，reclusterer 全开（默认参数：W=180s, S=30s, K∈[2,6],
link=0.55, ema=0.20, min_segs=12, max_segs=300，dual-encoder 384D）。

按系统级规则"语义判断禁止脚本打分"（`workflow.instructions.md`
§Semantic Evaluation，commit 40ab28d），agent 直接对照
`tests/fixtures/test_ground_truth.json` 阅读 transcript.md。以下为
*现象 → 证据 → 怀疑成因 → 候选干预*，不报 macro-F1。

### 现象一 — 首次 reclusterer 触发即把 4 个 GT 说话人坍缩成 2 个全局

**证据。** 600s 结束时的 forward-map 是 `{0,1,2,5} → 1000`、
`{3,4} → 1001`。GT 有四个说话人（朱杰 / 徐子景 / 唐云峰 / 石一），系统
最终只剩两个全局。所有合并都发生在 `t=03:24.500`（180s 预热后的第一个
窗口结束点）：单次窗口推断里 raw `0`、`1`、`2` 全部被映射到 global
`1000`，raw `3` 被映射到 `1001`。后续 `04:10.700`、`05:12.400` 的 pass
只是把这两个桶继续累加。

**怀疑成因。** 窗口内 K 选择看起来是健康的——eval driver 全语料日志里
"Optimal K=4 / K=5" 在多个窗口出现。所以坍缩的责任不在 spectral
clustering，而在 **跨窗口 Hungarian linker**。第一个窗口（00:00–03:00）
里 raw=0 主要承担朱杰的长独白（00:22–00:39，约 10 秒干净）；raw=1
散落在朱杰 / 徐子景 / 唐云峰 的短轮中；raw=3 在 01:42 才开始作为唐云峰
出现。Hungarian linker 面对一个仍被朱杰证据主导的 384D centroid，把
raw=1 + raw=2 + raw=0 都判为"同一 global"（链接阈值 0.55 在 EMA
centroid 尚未分离时太宽松），然后给 raw=3 单独分配一个 global。这印证
了 `2026-05-26.md` 的 Phase 14 工作假设："full_60m macro_f1 的瓶颈
在跨窗口 Hungarian 链接稳定性。"生产数据现在确认了这个判断。

**候选干预。**
- 把 linker 阈值 0.55 → 0.65 **仅在 bootstrap 阶段**生效（例如前
  N≤2 个窗口），或者让阈值随 EMA centroid 已吸收的 segment 数量动态
  收紧。
- 要求 linker 双向同意（候选必须同时是双方的最佳匹配，而不是单边
  "高于 0.55"）。
- bootstrap 延迟：`min_segs` 12 → ~24，或者强制至少 2 个窗口之后才允许
  发出第一个 relabel 事件。让 raw ID 先累积更厚的证据。

### 现象二 — 约 05:18 之后，4 个全局成型，系统自我修正

**证据。** `06:16.800` 起出现 raw `7`，到 `07:05` 都很干净——所有
overlap 都是 `GT=徐子景 pred=7`。`07:20.100` 起出现 raw `6`，在
`08:43` 之前主导石一区段（08:24/08:26 夹了两个唐云峰短句，因为石一/
唐云峰在快速对话）。关键是：raw=6 和 raw=7 **不在** forward-map 中，
reclusterer 从未尝试把它们合并。也就是说，一旦 4 个全局已经"挑出来"
且彼此分离够远，linker 是会保住身份的。病灶仅限于 bootstrap。

**含义。** 这是好消息——稳态行为是正确的。bug 局限于前 3–5 分钟，
EMA centroid 尚未成熟的阶段。一套"bootstrap 感知"的策略（延迟首次
relabel、年轻 centroid 期用更紧阈值）应当是高杠杆修复点。

### 现象三 — 一段长独白中途切换 global

**证据。** 唐云峰 03:27–03:58 的独白前半（03:27–03:43）是
`pred=1000`（raw=1），后半（03:47–03:55）是 `pred=1001`（raw=3）。
同一说话人、同一连续讲话，被打成两个不同全局。在线 linker 在同一段
speech event 里发出了 raw=1 和 raw=3 两个不同 raw ID；reclusterer
随后把 raw=1 映射到朱杰所在的 global（1000）、raw=3 映射到它自己的
global（1001）——把唐云峰的一段独白切成读起来是两个人。

**怀疑成因。** 上游 raw-cluster 碎片化：在线说话人识别 + 段落 linker
栈在一次连续讲话内发出多个 raw ID。reclusterer 本来就是来修这个的，
但它修的方向是错的，原因就是现象一。

**候选干预。** 修好现象一基本就修好这条——如果 raw=1 当初被关联到
raw=3（都是唐云峰）而不是 raw=0（朱杰），这段独白就连贯了。所以
linker 策略修复是关键路径。

### 现象四 — Margin-abstain 表现良好

**证据。** 约 25 个 `pred=-1`，几乎全部落在：(a) ≤0.5s 起始片段；
(b) 两人重叠区；(c) VAD 抓到但 speaker-ID 正确拒答的 "嗯/啊"
backchannel。没有一个 `pred=-1` 落在自信的长句上。保守 abstain 通路
工作正常，不是错误源。

**结论。** 此处无需修改。

### 现象五 — VAD 整段丢掉约 12 个短句

**证据。** "no runtime segment overlaps this utterance" 在前 600s 内
出现 12 次，全在 ≤2s 的话语（如 03:03 朱杰"啊？"、08:21 唐云峰"嗯。"、
09:26 徐子景"对."）。都是 backchannel 与单音节插入。

**怀疑成因。** SileroVAD / FSMN-VAD 的 min-speech-ms 门限太长，或者
25ms hangover 不足以保住孤立的"是/否"音节。这是 `sensus`（感知）问题，
不是 `orator` 问题。

**结论。** 出 Phase 3 范围。等后续对话理解栈开始关心 backchannel 时
再做 VAD 调参。

## Phase 3b.1 — 链接器审计（环境变量开关，eval 驱动 s600）

在 `src/orator/orator_reclusterer.cpp` 中加入了由
`DEUSRIDET_RECLUSTERER_DEBUG=1` 开关的审计输出。每次 spectral pass 会向
stderr 打印：(a) 每个 cluster 的成员列表（segment_id、raw_id、起止时间），
(b) 完整的 `cluster × global` 余弦矩阵并用方括号标出 Hungarian 的分配，
(c) 每行的 link_threshold 通过情况，(d) 每一次新 global 的分配，
(e) 每一次 global-merge 合并（含 sim），(f) 最终的 `local_to_global` 表。
默认关闭，关闭时零开销。

对相同的音频片段（即生成 s600 生产回放所用的部分）重新运行 eval：

```
DEUSRIDET_RECLUSTERER_DEBUG=1 \
  ./build/orator_reclusterer_eval \
  --fixture tests/fixtures/fused_v1.bin --end-sec 600 \
  --W 180 --S 30 --thr 0.55 --ema 0.20
→ macro_f1=0.9046 K_pred=5 K_mapped=4/4 n_scored=198 n_events=299
```

产物：`runs/20260527_audit_s600/audit.log`（451 行）。

### Phase 3c 推论被推翻

Phase 3c 曾假设 t=03:24.500 处存在「Hungarian 灾难性 4→2 过度合并」。
审计否决了这一推论：

1. **首窗 spectral 从未给出 K=4。** 实际 0-180s 的 GT 分布是
   朱杰 ≈62s 独白 + 唐云峰 ≈10s 短发言 + 徐子景 ≈5s + 石一 ≈3s，
   数据本身只够支撑两个稳定 cluster。K=2 正是这段数据该有的结果，
   Hungarian 链接器是清白的 — 根本没有四个 cluster 可以让它去合并。

2. **第 3、4、5 个 global 会随着窗口累积新材料而自然出现。**
   Global 1002 在 t≈132s 出现，1003、1004 在 t≈303–553s 之间出现。
   reclusterer「随窗口积累发现新说话人」的机制工作良好。

3. **离线 eval 与在线 live 之间存在显著差异。** Eval 到 s600
   有 5 个 global、macro_f1=0.9046；生产回放到 s600 只有 2 个 global
   （`{0,1,2,5}→1000, {3,4}→1001`）。同一段音频、同一份 reclusterer
   代码、同一份默认配置（W=180s、S=30s、thr=0.55、ema=0.20）。
   **bug 在于 live 管线喂给 reclusterer 的输入与 fixture 不同**，
   而不在 reclusterer 内部。

### H1 已证：`match.speaker_id >= 0` 门控吞掉 53% 的段

每条 REJECT 都是 `sid=-1 sim=0.000 is_new=0`。这些是 online identify
路径（campp / dual_db identify、recency absorb-guard、margin-abstain）选择
弃权的段，但其 fbank 是真实语音（fbank=188..528 帧 ≈ 1.9..5.3 秒）。
门控在 `audio_pipeline_process_saas_full.cpp` ~329 行直接把它们扔掉，
embedding 永远到不了 reclusterer。**reclusterer 的设计目的本来就是覆盖
online linker 的判断；用 online linker 的决策去过滤 reclusterer 的输入，
是结构上的语义倒置。**

### H2 已证：VAD 切片密度才是主因

即使忽略门控，live 600s 内总共只产出 72 个 FULL 抽取，而 fixture 同段
有 198 段（GT 对齐切割），密度差 2.75 倍。fixture 来自
`cam_embeddings_v1.meta.json`（GT 说话人轮次切分，~3s/段），live VAD 按
静音/重叠启发式切分，~8s/段。在 `min_segments=12`、W=180s 下，live 首
个 reclusterer pass 看到的窗口几乎全是 朱杰 ~62s monologue + 几段
唐云峰 短话，徐子景（0-600s GT 约 5s）与 石一（约 3s）样本太少形成不了
稳定簇，spectral 正确返回 K=2。

注：H2 不是"bug"——fixture 是按 GT 粒度人为过细切割的。live VAD 是
真实工况下的运行点。eval 的 `macro_f1=0.9046` 因此高估了可用 headroom。

### H3 排除：embedding 数值正常

所有 ACCEPT 报告 `L2=1.000000 dim=384`。dual embedding（CAM++ 192 ⊕
WL-ECAPA 192）按 fixture 构建时一致的方式做 L2 归一化，数值无偏。

### 优势杠杆

H1 是唯一干净、低风险的修复。去掉 `match.speaker_id >= 0` 一项后，
38 个段被救回（reclusterer 可见数 34 → 72，**+112%**）。72 段/600s 接近
fixture 在 t=583s pass 时 N=63 的密度（5 globals 稳定）。

计划 3b.3：用环境变量 `DEUSRIDET_RECLUSTERER_ACCEPT_ABSTAINED=1` 做 A/B；
abstain 段以 `tentative_speaker_id=-1` 入栈，RelabelEvent 报告 `old=-1`，
验证 WebUI patcher 能正确处理。

H2 承认为上游 VAD 的设计参数而非缺陷。收紧 live VAD 会减小段长但牺牲
纯度（更多 overlap 污染切片），本阶段不动。

H3 关闭。

## Phase 3b.3 — H1 修复 A/B 验证（成功）

在 [`src/sensus/auditus/audio_pipeline_process_saas_full.cpp`](src/sensus/auditus/audio_pipeline_process_saas_full.cpp)

### 结论

- Phase 3-14 的负面实验，量的其实是一个被门控饿死的 reclusterer ——
  53% 的真实语音段从未到达它面前。
- "macro_f1=0.7032 (full_60m) / 0.7935 (s1800 fixture)" 这些基线是在
  gate-free fixture 通路上测的，没暴露 live 门控丢弃 bug。
- Reclusterer 的默认参数 (W=180, S=30, link=0.55, centroid_ema=0.20,
  min_k=2, max_k=6) 在这个工况下是对的。不需要再调任何 reclusterer
  旋钮；bug 在上游，一个 env-gated 布尔就能修。
- 修复保持 env-gated (`DEUSRIDET_RECLUSTERER_ACCEPT_ABSTAINED=1`)，默认
  生产行为不变。要真正常开，应放在一次独立变更里，并要先有第二段长音频
  复现该结果。
