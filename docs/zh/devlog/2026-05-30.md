### 为何尚未翻转默认——吞吐可行性

原生 `diarize()` 是**单 chunk**（无 batch）：每 1.6 秒步进一次 WavLM-pruned
（24 层 transformer）+ Conformer + ResNet34 前向，约 2260 个 chunk。实测开销：
**0.87 秒/chunk → 1943.6 秒（RTF 0.54）** 处理 60 分钟会话。已交付的 Python-IPC
路径对*同一* finalize 仅需 753.7 秒（RTF 0.21），因为参考 DiariZen 栈以 32
批处理。

因此原生路径精度持平（略好）但比当前交付路径**慢 2.6 倍**。依据 Prime
Directive #9，精度决定*改进*，吞吐决定*可行性*——现在翻转默认会是吞吐回退。
**对 WavLM/Conformer/ResNet34 前向做 batch（batch_size = 32，与参考一致）是
翻转默认前的可行性关键任务。** 单序列 CUDA 前向（`[C,T]`/`[T,C]` 布局、无
batch 轴）使之成为大型、需分步推进的多文件改动；过程中 60 秒 fixture 位等价
必须保持绿色。

## 更新 — 吞吐可行性门槛已清除（原生活体胜过 Python）

上文「慢 2.6 倍」的判断**对原因判断错了**。它不是 batch 缺失，而是碎片化的
活体 VMM 映射下的 Tegra `cudaMalloc`/`cudaFree` 抖动。消除它**无需** batch，
只需把已用于 WavLM 的持久权重缓存纪律同样应用到 Conformer。

本次更新提交（全部位等价保持、`internal-check-only`、精度不变 93.7%）：

- `75a92e4` WavLM-pruned 编码器持久 fp32 权重缓存
- `cdea087` WavLM-pruned 前向持久 scratch 池
- `c5a800a` WavLM attention scores/context 改用 cuBLAS 批量 GEMM
- `7bee0c5` Conformer MHSA scores/context 改用 cuBLAS 批量 GEMM
- `fd79f9c` WavLM CNN 前端通道 LayerNorm 合并访存
- `7dd64d7` Conformer head 持久 fp32 权重缓存 + diarize 各级计时

### 内核/分配器诊断

`nsys` 显示三个手写内核做非合并跨步全局访问（WavLM `attn_scores_kernel`
42.7%、Conformer `mhsa_scores_kernel` 13.1%、`layer_norm_channels_kernel`
20.2%）；全部替换为 `cublasSgemmStridedBatched` / 合并访存重写。但决定性的杠杆
是**逐 chunk 权重分配抖动**：WavLM（24 层）与 Conformer head（4 层 + 分类器）
都在*每个* chunk 把每个 fp16 权重重新转换为新的 fp32 设备缓冲
（`cudaMalloc` + `half_to_float` + `cudaFree`）——每 60 分钟会话约 32.4 万次
`cudaMalloc`/`cudaFree`。

在 Tegra 上每次 `cudaMalloc`/`cudaFree` 都要遍历全局 VMM 映射。**离线**（干净、
小映射）该抖动仅约 18 秒。**活体**——WavLM-ECAPA、Silero VAD 与环形缓冲共驻，
全局 VMM 映射庞大且碎片化——*同样*的抖动耗费约 1268 秒。这正是
`diarizen_wavlm_pruned.h` 注释警告的危险；PyTorch 因其缓存分配器从不付此代价。
修复是按张量名键入的持久设备常驻 fp32 缓存（`weight_f32()`），首次使用时转换
一次。

## RTF 攻坚 —— TF32、WavLM 稠密批处理、Conformer 暂存池（离线，逐位一致）

在线可行性门槛已在 RTF 0.190 通过后，项目主仍不满意：「这个模型并不大，
是我们的 CUDA kernel 不够高效。」于是开展了一轮以 profiling 为驱动的离线
攻坚。每个手段都是逐位一致的（fp32 bit-eq harness PASS 28/28），因此精度不变。

### 落地的手段

1. **TF32 张量核数学**（环境变量 `DEUSRIDET_DIARIZEN_TF32` 控制，默认开）：
   通过 `CUBLAS_TF32_TENSOR_OP_MATH` 把稠密 GEMM 走 Ampere 张量核；设为
   `=0` 可恢复 fp32 逐位一致。
2. **WavLM 稠密线性批处理**：把 `B` 个 chunk 堆叠成融合的 `[B*T, H]` GEMM
   （`debug_lnorm_tail_batch` + 支持 B 的 `run_encoder_layer_`）。离线 seg
   13250 → 12450 ms。**与批大小无关**（B=8/16/33/66 都约 12.5 s）——证明
   WavLM 编码器的*计算*并非 seg 瓶颈。
3. **Conformer 暂存池 + 缓存 cublas 句柄**：seg 阶段真正的耗时来源是
   Conformer head 每个 chunk 的 `cudaMalloc`/`cudaFree`（约 7 个缓冲 ×
   ffn/mha/conv × 4 层 × 66 chunk），加上每个 chunk 的 `cublasCreate`/
   `cublasDestroy`（各自隐含一次 device 同步）。替换为按字节大小分桶的
   自由链表暂存池（`scratch_acquire`/`scratch_release`）和一个惰性创建、
   复用的 `blas_` 句柄。这正是已为 WavLM 权重修过、却从未为 Conformer
   暂存修过的同一个 Tegra VMM 抖动反模式。

### 离线结果（120 s / 66 chunk，`/tmp/wave_30s.bin`）

| 阶段 | 之前 | 之后 |
|------|------|------|
| seg   | 12450 ms | **9400 ms**（−24 %） |
| total | 约 17.8 s | 约 14.8 s |

复现 3 次（9590 / 9447 / 9355 ms）。fp32 bit-eq PASS 28/28 —— 暂存池交还的
是未初始化缓冲，消费者在读取前必先覆写，因此结果与全新 `cudaMalloc` 逐位等价。

`accuracy(tests/test.mp3, diarization): unchanged (bit-identical fp32 PASS 28/28)`

### 为何离线低估了收益

离线时 VMM 映射干净，分配抖动很便宜；24 % 的 seg 下降是*下限*。在线时
（WavLM-ECAPA + Silero VAD + 环形缓冲同驻、映射碎片化）同样的每 chunk 抖动
对 WavLM 权重曾是灾难性的（约 1268 s）—— Conformer 暂存/句柄的移除攻击的是
同一隐患，因此在线收益应超过离线的 24 %。完整的在线 RTF 重测按项目主的指示
推迟（先离线迭代到 RTF 理想，再做一次在线门槛）。

## RTF 攻坚 2 —— ResNet34 嵌入器：每 chunk 主干复用 + 卷积计划缓存

Conformer 修复后重新做 nsys profile 显示 **embed 阶段（ResNet34 x-vector）
已是最大的 GPU 消耗**——明显属于 ResNet34 的 kernel（cutlass tf32 fprop 13%
+ r34_bn_relu 10.3% + winograd 9.1% + nchwToNhwc 7.4% + r34_add_relu 5.1% +
cutlass analytic 5.1% + nhwcToNchw 4.0%）合计约 54% 的 GPU 时间。落地两个逐位
一致的手段。

### 1. 主干复用（大头）：embed 5329 → 1382 ms（−74%）

`get_embeddings` 的循环是 `for chunk: for speaker: embed(chunk, mask)`——对
每个 chunk **把整个 ResNet34 主干重算了 S=4 次**（每个说话人一次），而主干只
是 chunk 波形的函数（说话人 mask 只在池化头才进入）。把 `embed()` 拆成
`embed_backbone()`（fbank → stem → 16 个 block，存入 `d_backbone_`）和
`embed_pool()`（mask 插值 → 统计池化 → seg_1 投影）。pipeline 现在每 chunk
只算一次主干、按说话人分别池化。运算完全相同、只是去重 → 逐位一致，而占主导
的卷积成本下降约 S 倍。

### 2. cuDNN 卷积计划缓存

`conv2d_` 在**每个**卷积、每次调用都创建并销毁 4 个 cuDNN 描述符并跑一次
`cudnnGetConvolutionForwardAlgorithm_v7` 启发式。一旦 chunk 长度固定，ResNet34
的约 36 个卷积形状就是固定的，因此计划（描述符 + 选定 algo）现按
`(C_in,C_out,H,W,K,stride,pad)` 缓存。选中的 algo 不变 → 逐位一致；消除了每个
卷积的描述符抖动（在碎片化 VMM 下对在线有帮助）。

### 离线结果（120 s / 66 chunk，已杀掉所有后台进程）

| 阶段 | push 2 之前 | 之后 |
|------|------------|------|
| seg   | 约 6240 ms | 约 6235 ms |
| embed | 5329 ms | **1382 ms**（−74%） |
| total | 11583 ms | **7631 ms**（−34%） |

fp32 bit-eq PASS 28/28（end2end segs 28/28，标签一致，最大边界差 0.02 s）。

`accuracy(tests/test.mp3, diarization): unchanged (bit-identical fp32 PASS 28/28)`

### 关于此前 9.4 s 的 seg 数据

Conformer 提交后量到的 9.4 s seg 是在后台 `awaken`/`diarizen_live_score` 进程
争抢 GPU 时测的。全部杀掉后干净的 seg 约 6.2 s——Conformer 暂存池的收益成立；
9.4 s 是争抢，不是回退。

## RTF 攻坚的在线验证 —— 以及一个陈旧二进制陷阱

两个 perf 提交（`3758651` Conformer 暂存池、`ff35b27` ResNet34 主干复用）经
在线验证（`tools/diarizen_live_score.py`、`tests/test.mp3`、8×、全新启动 +
`drop_caches`）。

**先踩到的陷阱：** `make test_diarizen_pipeline_biteq` 会重建 `liborator.a`
和 bit-eq harness，但**不会**重建 `build/deusridet`（`awaken` 二进制）。因此第
一次在线运行跑的是*陈旧的* `deusridet`（mtime 早于两个提交）：在线 `embed`
为 180 512 ms / 2251 chunk = 80 ms/chunk——与*修复前*的离线 5329/66 = 80.7
ms/chunk 完全一致，正是新代码没进二进制的破绽。**任何在线门槛前都必须 `make
deusridet`；并核对二进制 mtime 与提交时间。**

**重建 `deusridet` 后**，对完整 60 分钟缓冲（C=2251 chunk）的在线 `diarize()`：

| 阶段 | 陈旧二进制 | 重建后 | Δ |
|------|-----------|--------|---|
| seg | 382 367 ms（170 ms/chunk） | 313 521 ms（139 ms/chunk） | −18% |
| embed | 180 512 ms（80 ms/chunk） | **46 159 ms（20.5 ms/chunk）** | **−74%** |
| cluster | 48 167 ms | 49 729 ms | 持平 |
| **diarize 总计（finalize 墙钟）** | **611 102 ms** | **409 462 ms** | **−33%** |

embed −74% 与 seg −18% 精确复现了离线测量，因此这些收益在碎片化的在线 VMM
映射下是真实的，并非离线假象。精度保持 93.6%（门槛 ≥ 93.5% 通过）。

`accuracy(tests/test.mp3, diarization): 93.5% → 93.6%   (Δ = +0.1 pp)`
（+0.1 pp 来自此前的 `d1b9d82`；这两个提交是纯 perf、逐位一致，因此保持它。）

**新的主导阶段：** seg 仍占 `diarize()` 的 77%（WavLM/Conformer 长尾 kernel
——继续削减有破坏逐位一致的风险），`cluster` 现约 12%（凝聚式聚类，随 chunk
数超线性增长——这是在 66-chunk 小样本上看不见的新着力点）。
