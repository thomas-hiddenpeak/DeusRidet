## 更新 — 吞吐可行性门槛已清除（原生活体胜过 Python）

上文「慢 2.6 倍」的判断**对原因判断错了**。它不是 batch 缺失，而是碎片化的
活体 VMM 映射下的 Tegra `cudaMalloc`/`cudaFree` 抖动。消除它**无需** batch，
只需把已用于 WavLM 的持久权重缓存纪律同样应用到 Conformer。

本次更新提交（全部位等价保持、`internal-check-only`、精度不变 93.7%）：

- `75a92e4` WavLM-pruned 编码器持久 fp32 权重缓存
- `cdea087` WavLM-pruned 前向持久 scratch 池
- `c5a800a` WavLM attention scores/context 改用 cuBLAS 批量 GEMM
- `7bee0c5` Conformer MHSA scores/context 改用 cuBLAS 批量 GEMM
- `fd79f9c` WavLM CNN 前端通道 LayerNorm 合并访存
- `7dd64d7` Conformer head 持久 fp32 权重缓存 + diarize 各级计时

### 内核/分配器诊断

`nsys` 显示三个手写内核做非合并跨步全局访问（WavLM `attn_scores_kernel`
42.7%、Conformer `mhsa_scores_kernel` 13.1%、`layer_norm_channels_kernel`
20.2%）；全部替换为 `cublasSgemmStridedBatched` / 合并访存重写。但决定性的杠杆
是**逐 chunk 权重分配抖动**：WavLM（24 层）与 Conformer head（4 层 + 分类器）
都在*每个* chunk 把每个 fp16 权重重新转换为新的 fp32 设备缓冲
（`cudaMalloc` + `half_to_float` + `cudaFree`）——每 60 分钟会话约 32.4 万次
`cudaMalloc`/`cudaFree`。

在 Tegra 上每次 `cudaMalloc`/`cudaFree` 都要遍历全局 VMM 映射。**离线**（干净、
小映射）该抖动仅约 18 秒。**活体**——WavLM-ECAPA、Silero VAD 与环形缓冲共驻，
全局 VMM 映射庞大且碎片化——*同样*的抖动耗费约 1268 秒。这正是
`diarizen_wavlm_pruned.h` 注释警告的危险；PyTorch 因其缓存分配器从不付此代价。
修复是按张量名键入的持久设备常驻 fp32 缓存（`weight_f32()`），首次使用时转换
一次。

## RTF 攻坚 —— TF32、WavLM 稠密批处理、Conformer 暂存池（离线，逐位一致）

在线可行性门槛已在 RTF 0.190 通过后，项目主仍不满意：「这个模型并不大，
是我们的 CUDA kernel 不够高效。」于是开展了一轮以 profiling 为驱动的离线
攻坚。每个手段都是逐位一致的（fp32 bit-eq harness PASS 28/28），因此精度不变。

### 落地的手段

1. **TF32 张量核数学**（环境变量 `DEUSRIDET_DIARIZEN_TF32` 控制，默认开）：
   通过 `CUBLAS_TF32_TENSOR_OP_MATH` 把稠密 GEMM 走 Ampere 张量核；设为
   `=0` 可恢复 fp32 逐位一致。
2. **WavLM 稠密线性批处理**：把 `B` 个 chunk 堆叠成融合的 `[B*T, H]` GEMM
   （`debug_lnorm_tail_batch` + 支持 B 的 `run_encoder_layer_`）。离线 seg
   13250 → 12450 ms。**与批大小无关**（B=8/16/33/66 都约 12.5 s）——证明
   WavLM 编码器的*计算*并非 seg 瓶颈。
3. **Conformer 暂存池 + 缓存 cublas 句柄**：seg 阶段真正的耗时来源是
   Conformer head 每个 chunk 的 `cudaMalloc`/`cudaFree`（约 7 个缓冲 ×
   ffn/mha/conv × 4 层 × 66 chunk），加上每个 chunk 的 `cublasCreate`/
   `cublasDestroy`（各自隐含一次 device 同步）。替换为按字节大小分桶的
   自由链表暂存池（`scratch_acquire`/`scratch_release`）和一个惰性创建、
   复用的 `blas_` 句柄。这正是已为 WavLM 权重修过、却从未为 Conformer
   暂存修过的同一个 Tegra VMM 抖动反模式。

### 离线结果（120 s / 66 chunk，`/tmp/wave_30s.bin`）

| 阶段 | 之前 | 之后 |
|------|------|------|
| seg   | 12450 ms | **9400 ms**（−24 %） |
| total | 约 17.8 s | 约 14.8 s |

复现 3 次（9590 / 9447 / 9355 ms）。fp32 bit-eq PASS 28/28 —— 暂存池交还的
是未初始化缓冲，消费者在读取前必先覆写，因此结果与全新 `cudaMalloc` 逐位等价。

`accuracy(tests/test.mp3, diarization): unchanged (bit-identical fp32 PASS 28/28)`

### 为何离线低估了收益

离线时 VMM 映射干净，分配抖动很便宜；24 % 的 seg 下降是*下限*。在线时
（WavLM-ECAPA + Silero VAD + 环形缓冲同驻、映射碎片化）同样的每 chunk 抖动
对 WavLM 权重曾是灾难性的（约 1268 s）—— Conformer 暂存/句柄的移除攻击的是
同一隐患，因此在线收益应超过离线的 24 %。完整的在线 RTF 重测按项目主的指示
推迟（先离线迭代到 RTF 理想，再做一次在线门槛）。

## RTF 攻坚 2 —— ResNet34 嵌入器：每 chunk 主干复用 + 卷积计划缓存

Conformer 修复后重新做 nsys profile 显示 **embed 阶段（ResNet34 x-vector）
已是最大的 GPU 消耗**——明显属于 ResNet34 的 kernel（cutlass tf32 fprop 13%
+ r34_bn_relu 10.3% + winograd 9.1% + nchwToNhwc 7.4% + r34_add_relu 5.1% +
cutlass analytic 5.1% + nhwcToNchw 4.0%）合计约 54% 的 GPU 时间。落地两个逐位
一致的手段。

### 1. 主干复用（大头）：embed 5329 → 1382 ms（−74%）

`get_embeddings` 的循环是 `for chunk: for speaker: embed(chunk, mask)`——对
每个 chunk **把整个 ResNet34 主干重算了 S=4 次**（每个说话人一次），而主干只
是 chunk 波形的函数（说话人 mask 只在池化头才进入）。把 `embed()` 拆成
`embed_backbone()`（fbank → stem → 16 个 block，存入 `d_backbone_`）和
`embed_pool()`（mask 插值 → 统计池化 → seg_1 投影）。pipeline 现在每 chunk
只算一次主干、按说话人分别池化。运算完全相同、只是去重 → 逐位一致，而占主导
的卷积成本下降约 S 倍。

### 2. cuDNN 卷积计划缓存

`conv2d_` 在**每个**卷积、每次调用都创建并销毁 4 个 cuDNN 描述符并跑一次
`cudnnGetConvolutionForwardAlgorithm_v7` 启发式。一旦 chunk 长度固定，ResNet34
的约 36 个卷积形状就是固定的，因此计划（描述符 + 选定 algo）现按
`(C_in,C_out,H,W,K,stride,pad)` 缓存。选中的 algo 不变 → 逐位一致；消除了每个
卷积的描述符抖动（在碎片化 VMM 下对在线有帮助）。

### 离线结果（120 s / 66 chunk，已杀掉所有后台进程）

| 阶段 | push 2 之前 | 之后 |
|------|------------|------|
| seg   | 约 6240 ms | 约 6235 ms |
| embed | 5329 ms | **1382 ms**（−74%） |
| total | 11583 ms | **7631 ms**（−34%） |

fp32 bit-eq PASS 28/28（end2end segs 28/28，标签一致，最大边界差 0.02 s）。

`accuracy(tests/test.mp3, diarization): unchanged (bit-identical fp32 PASS 28/28)`

### 关于此前 9.4 s 的 seg 数据

Conformer 提交后量到的 9.4 s seg 是在后台 `awaken`/`diarizen_live_score` 进程
争抢 GPU 时测的。全部杀掉后干净的 seg 约 6.2 s——Conformer 暂存池的收益成立；
9.4 s 是争抢，不是回退。

## DiariZen 聚类——凝聚步骤从 CPU 移到 GPU（逐位一致）

`accuracy(tests/test.mp3, diarization): unchanged (bit-identical fp32 PASS 28/28; full-session output BYTE-IDENTICAL)`

### "全程都在跑"的那颗 CPU

Thomas 观察到整个测试过程中有一颗 CPU 核心被占满。seg 与 embed 阶段已经常驻
GPU（cuDNN / cuBLAS），因此 `diarize()` 里仅剩的持续*纯 CPU*计算就是**聚类**
阶段。一个 env 门控的子阶段 profiler（`DEUSRIDET_DIARIZEN_CLUSTER_PROF=1`，
输出一行 `[cluster-prof]`）对完整 60 分钟会话（C=2251 chunk，N=3894 叶子）
定位了元凶：

```
[cluster-prof] N=3894 K0=533 Kc=4 C=2251 S=4 |
  filter=20.3  ahc=40949.4  fea=305.8  vbx=6438.1  cent=1.4  soft=11.9  assign=1.1  total=47730.1 ms
```

凝聚式质心连接合并（`ahc`）占了聚类墙钟的 **40 949 ms = 86%**，且是一段单一、
不间断的 CPU 燃烧——正是那颗"全程都在跑"的核心。合并本身是 `n−1` 个依赖步
骤，但每步的两项重活是数据并行的：活跃对集合上的全局最小值扫描（O(active²)）
与 Lance-Williams 质心更新（O(active)），外加一次性的成对距离（O(n²)）。

### 交付内容

`src/orator/diarizen_clustering_ahc.{cu,h}`——GPU 质心连接合并：

- `pdist_kernel`：每对 (i,j) 一个线程，沿嵌入维度做**顺序 fp64 累加**——
  保持 CPU 求和顺序，不做归约。
- `argmin_kernel` + `reduce_kernel`：对活跃对集合做块内归约，使用
  **字典序 (dist, i, j) 比较器**，逐位复现 CPU 的"行主序扫描中第一个严格
  更小者"的平局规则。
- `lw_kernel`：Lance-Williams 质心更新，精确镜像 `centroid_lw` 的 fp64
  运算顺序。
- 主机驱动跑串行 `n−1` 合并循环，在主机上记录树（亚毫秒）；fcluster DFS
  编号与 MD 计算留在 CPU（极小、串行）。任何 CUDA 错误即返回 `false`，
  `agglomerative_()` 原样回退到原 CPU 路径。

### 结果（完整 60 分钟会话，离线 profile）

```
[cluster-prof] N=3894 K0=533 Kc=4 C=2251 S=4 |
  filter=20.0  ahc=3669.3  fea=308.5  vbx=6015.0  cent=1.4  soft=11.9  assign=1.1  total=10028.7 ms
```

| 子阶段 | CPU | GPU | Δ |
|--------|-----|-----|---|
| ahc | 40 949.4 ms | **3 669.3 ms** | **−91.0%** |
| cluster 总计 | 47 730.1 ms | **10 028.7 ms** | **−79.0%** |
| diarize 总计 | 369 879 ms | **332 468 ms** | **−10.1%** |

**逐位一致用两种方式证明：** (1) 29-chunk 小样本 bit-eq harness
`RESULT: PASS`（segs 28/28，labels_match，`min_cos=0.999980`）；(2)——更强
——对真实 60 分钟音频的完整会话输出是**逐字节一致**的：
`cmp /tmp/out_full.bin /tmp/out_full2.bin → BYTE-IDENTICAL`（20196/20196 字节）。
因此精度可证地保持 93.6%；只有 CPU 燃烧被移到了 GPU。

**Tegra 内存说明：** 合并会分配一个瞬态成对距离缓冲 `dD`，大小
`total² × 8 B`（N=3894 时约 485 MB），在每次 `diarize()` 结束时释放

故 2 小时会话需约 2 GB（本次不在范围内）。

**新的主导聚类子阶段：** `ahc` 移出 CPU 后，**VBx（6 015 ms，仍在 CPU）**
成为最大的聚类 CPU 消耗。文档 `12-diarizen.md` 风险 #3 曾把 VBx 留在 CPU，
注明"只有当 profiling 显示它重要时才提升到 GPU"——现在它重要了，但 VBx

## DiariZen `diarize()` 子阶段 profile —— finalize 已是 GPU 主导

`accuracy(tests/test.mp3, diarization): unchanged (env-gated timers only, bit-identical)`

反复出现的担忧是"CPU 全程在跑"——所以在再移植任何东西到 GPU 之前，先测量
`diarize()` finalize 的墙钟时间究竟花在*哪里*。新增了两个 env 门控的子阶段
profiler，沿用既有的 `DEUSRIDET_DIARIZEN_CLUSTER_PROF=1` 范式：

- `DEUSRIDET_DIARIZEN_SEG_PROF=1` → `[seg-prof]` 把分段阶段拆成 `fill`
  （主机 chunk 拷贝）/ `wavlm`（GPU 编码器）/ `conf`（GPU Conformer）/
  `decode`（主机 powerset argmax）。
- `DEUSRIDET_DIARIZEN_EMB_PROF=1` → `[emb-prof]` 把嵌入阶段拆成 `backbone`
  （GPU ResNet34，每 chunk 一次）/ `pool`（GPU 掩码统计，每 chunk S 次）。

两者都是 `getenv` 门控后的纯 `std::chrono` 计时器；默认关闭，零运行时开销，
且逐位一致（小样本 bit-eq `RESULT: PASS`，segs 28/28，`min_cos=0.999980`）。

### 结果（完整 60 分钟会话，离线 profile，C=2251）

```
[seg-prof]     C=2251 B=8 T=799 | fill=271.4  wavlm=261417.4  conf=14076.5  decode=71.6 ms
[emb-prof]     C=2251 S=4       | backbone=10143.0  pool=36065.9 ms
[cluster-prof] N=3894 K0=533 Kc=4 ... vbx=6436.5 ... total=10453.1 ms
diarize stages: seg=276258  embed=46614  cluster=10453  post=53  binarize=1  total=333379 ms
```

| 位置 | ms | 设备 | 说明 |
|------|----|------|------|
| WavLM-pruned 编码器 | 261 417 | **GPU** | 24 层 transformer，占 `diarize()` 78% |
| Conformer head | 14 076 | **GPU** | 每 chunk batch=1，4% |
| ResNet34 backbone+pool | 46 209 | **GPU** | 14% |
| AHC 聚类 | 3 669 | **GPU** | 已移植（commit 2263918） |
| VBx EM | 6 436 | CPU | 唯一持续的主机计算，1.9% |
| 主机 glue（fill+decode+post） | ~395 | CPU | 一次性簿记，0.1% |

### 结论 —— `diarize()` 中已无持续 CPU 热点

finalize **已经符合 GPU-first**。seg 阶段（占 78% 的大头）是 99.9% 的 GPU
transformer 计算——其主机侧只有 `fill` 271 ms + `decode` 72 ms（亚秒级的
一次性拷贝 + argmax，正是 GPU-first 准则允许留在 CPU 的"微小串行 glue"）。
embed 与 AHC 都在 GPU。唯一剩下的持续 CPU 计算是 **VBx EM = 6 436 ms**
（占 `diarize()` 的 1.9%）。

VBx 留在 CPU 是**有意决策**，而非遗漏：

1. 它是**仅 finalize 的突发**——`diarize()` 每会话只跑一次；live RTF 已是
   0.19，VBx 对它的贡献约 0.002。GPU 移植无法撼动可行性门槛。
2. 它**逐位脆弱**。VBx 是带 ELBO 收敛 break 的 20 迭代贝叶斯-HMM EM；把它
   的两个 fp64 GEMM 走 cuBLAS DGEMM 无法复现 CPU 的顺序 FMA-收缩求和顺序，
   于是一个微小的舍入差异就可能让收敛错开一个迭代并*静默*改变聚类归属
   ——这正是宪法（规则 #9）警告的静默精度回归类。它会放弃廉价的逐字节
   门槛，并为一个 6 s 的突发强制 40 分钟的 live 精度验证，却无任何吞吐或
   精度收益。

因此正确的做法是**到此为止**："CPU 全程在跑"的观察其实是 CPU 在漫长的
WavLM 前向中忙等 GPU kernel 启动/同步，而非可以搬迁的主机计算。profiler
以 env 门控保留为永久诊断，任何未来的回归只需一个 `getenv` 即可看见。

## P3c 默认翻转 gate —— LLM 加载 native 复测，修复两个阻塞

`accuracy(tests/test.mp3, diarization): 93.5% → 93.6%   (Δ = +0.1 pp)`

P3c gate 要求 native DiariZen 路径在**27B LLM 加载**
（`DEUSRIDET_TEST_WS_ENABLE_LLM=1`）下 live 保持 ≥ 93.5 %，因为 holdback
worker 仅在有 LLM 消费重标转写时才激活。该配置此前从未产出 accuracy 行——
运行直接崩溃。定位过程暴露出两个独立 bug。

### 阻塞 1 —— periodic worker O(N²) 重新 diarize 污染 CUDA context

`DiarizenPeriodicWorker::run_one_pass_()` 每 60 s 对**整段**累积会话重新
diarize。代价 O(N)/趟 × N/period 趟 = O(N²)。live 日志显示三趟定时 pass：
C=130（16.8 s）、C=514（70 s）、C=1165（**211 s**）——单个后期 pass 独占共享
GPU 3.5 分钟，饿死 live 感知流水线（FRCRN 增强 + Silero VAD + WavLM-ECAPA
说话人识别）。音频 ring buffer 溢出 91,612 次；FRCRN 随后撞上 illegal memory
access（内存压力故障在首个 GPU 同步点浮现），整个 CUDA context 被污染，最终
整段 diarize 永不运行——因此没有广播 `speaker_diarize_final`，score client 挂
死。这正是旧 IPC "P2-verify" 行记录的失败（"worker 再 extract 死循环"），现已
精确定位：worker 仅在 LLM 加载时运行，这也是此前四次无 LLM gate 都干净
（RTF 0.19）的原因。

**修复 (A)。** 定时节奏现改为 `DEUSRIDET_DIARIZEN_PERIODIC=1` 门控（默认
**OFF**）。默认 worker 仅在显式 `diarizen_trigger` 或会话结束的
`diarizen_finalize` 时 diarize——流式期间不做整段重 diarize，无 GPU 独占、无
饥饿、无 context 污染。会话中实时重标改为 opt-in。整段重 diarize 设计与共享
GPU 上的进程内 native 路径根本不兼容。

**修复 (D，加固)。** `FrcrnGpu::enhance()`（设备路径）补上了 `enhance_host`
早已有的 `if (n_samples > max_samples_) return 0;` 边界钳制——过长 chunk 产生
超出 conv buffer 尺寸的 STFT 帧，溢出 cuDNN ConvT2d → `BAD_PARAM` → illegal
access。纵深防御；不触碰前向数学（bit-eq 不变）。

### 阻塞 2 —— LLM 加载 finalize 广播 schema 不匹配

LLM 加载时，`diarizen_finalize` 走 `worker->finalize()`（非 native-direct
路径）。worker 的广播用对象形 segment `{start,end,label}` 且无 `ok` 字段，而
live score client 需要 `final.get("ok")` 为真**且** segment 为数组形
`[start,end,label]`。因此每次 LLM 加载 finalize 都无法评分
（`[diarize] FAILED: unknown`）。修复：广播改为带 `ok` + 数组形 segment +
`audio_sec`/`wall_sec` + `n_segments`，同时保留 `segment_count`/`pass`/
`origin_sec`/`changed_pending`。WebUI 面板本就兼容两种 segment 形式，故不受
影响；空 segment 的 final 现也会广播显式 error，client 不再挂死。

### Live 验证（宪法 gate）

干净运行（`kill` + `fuser` + `drop_caches`），native DiariZen + 27B LLM
加载，holdback 激活，`tools/diarizen_live_score.py` 8× 回放：

- 1653 segment，`audio_sec=3615.12`，finalize `wall_sec=369.4`（**RTF 0.10**）
- 527 / 531 decided，coverage 0.992，macro = 0.916，**micro = 0.936**
- 各说话人：唐云峰 0.939 · 徐子景 0.920 · 朱杰 0.835 · 石一 0.971
- **0 FRCRN illegal/BAD_PARAM，0 periodic GPU 独占，无 context 污染**
- **`accuracy(tests/test.mp3, diarization): 93.5% → 93.6%   (Δ = +0.1 pp)`**

P3a fixture bit-eq 仍 PASS（28/28，min_cos 0.999980）——所有改动都不触碰
`diarize()` 数学。P3c LLM 加载 gate 已通过。
