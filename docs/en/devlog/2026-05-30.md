### Why the default is NOT flipped yet — throughput feasibility

The native `diarize()` is **single-chunk** (no batching): one WavLM-pruned
(24 transformer layers) + Conformer + ResNet34 forward per 1.6 s step, over
~2260 chunks. Measured cost: **0.87 s/chunk → 1943.6 s (RTF 0.54)** for the

753.7 s (RTF 0.21) because the reference DiariZen stack batches at 32.

So the native path is accuracy-parity (slightly better) but **2.6× slower**

throughput regression. **Batching the WavLM/Conformer/ResNet34 forwards
(batch_size = 32, like the reference) is the gating perf task before the
default-flip.** The single-sequence CUDA forwards (`[C,T]`/`[T,C]` layouts,
no batch axis) make this a large, paced multi-file change; the 60 s-fixture
bit-equality must stay green throughout.

## UPDATE — throughput feasibility gate CLEARED (native beats Python live)

The "2.6× slower" verdict above was **wrong about the cause**. It was not a
batching deficit — it was Tegra `cudaMalloc`/`cudaFree` churn under a
fragmented live VMM map. Closing it required *no* batching, only the same
persistent-weight-cache discipline already applied to WavLM.

Commits this update (all bit-equality-preserving, `internal-check-only`,
accuracy unchanged at 93.7 %):

- `75a92e4` persistent fp32 weight cache in WavLM-pruned encoder
- `cdea087` persistent scratch pool in WavLM-pruned forward
- `c5a800a` cuBLAS batched GEMM for WavLM attention scores/context
- `7bee0c5` cuBLAS batched GEMM for Conformer MHSA scores/context
- `fd79f9c` coalesce channel LayerNorm in WavLM CNN frontend
- `7dd64d7` persistent fp32 weight cache in Conformer head + diarize stage timing

### The kernel/allocator diagnosis

`nsys` showed three hand-rolled kernels doing uncoalesced strided global
work (WavLM `attn_scores_kernel` 42.7 %, Conformer `mhsa_scores_kernel`
13.1 %, `layer_norm_channels_kernel` 20.2 %); all replaced with
`cublasSgemmStridedBatched` / coalesced rewrites. But the decisive lever was
the **per-chunk weight allocation churn**: both WavLM (24 layers) and the
Conformer head (4 layers + classifier) re-converted every fp16 weight to a
fresh fp32 device buffer (`cudaMalloc` + `half_to_float` + `cudaFree`) on
*every* chunk — ~324 K `cudaMalloc`/`cudaFree` calls per 60-min session.

On Tegra every `cudaMalloc`/`cudaFree` walks the global VMM map. **Offline**
(clean, small map) this churn cost only ~18 s. **Live** — with WavLM-ECAPA,
Silero VAD and the ring buffers co-resident, the global VMM map is large and
fragmented — the *same* churn cost ~1268 s. This is exactly the hazard the
`diarizen_wavlm_pruned.h` comment warns about; PyTorch never pays it because
of its caching allocator. The fix is a persistent device-resident fp32 cache
keyed by tensor name (`weight_f32()`), converting once at first use.

## RTF push — TF32, WavLM dense batching, Conformer scratch pool (offline, bit-identical)

After the live feasibility gate cleared at RTF 0.190, the owner was still
dissatisfied: "this model isn't large — it's that our CUDA kernels aren't
efficient." A profiling-driven offline push followed. Each lever is
bit-identical (fp32 bit-eq harness PASS 28/28), so accuracy is unchanged.

### Levers landed

1. **TF32 tensor-core math** (env-gated `DEUSRIDET_DIARIZEN_TF32`, default ON):
   route the dense GEMMs through Ampere tensor cores via
   `CUBLAS_TF32_TENSOR_OP_MATH`. fp32 bit-eq is preserved by setting `=0`.
2. **WavLM dense-linear batching**: stack `B` chunks into fused `[B*T, H]`
   GEMMs (`debug_lnorm_tail_batch` + B-aware `run_encoder_layer_`). Offline
   seg 13250 → 12450 ms. **Batch-size invariant** (B=8/16/33/66 all ~12.5 s)
   — proof the WavLM encoder *compute* is not the seg bottleneck.
3. **Conformer scratch pool + cached cublas handle**: the real seg-stage
   drain was the Conformer head's per-chunk `cudaMalloc`/`cudaFree` (~7
   buffers × ffn/mha/conv × 4 layers × 66 chunks) plus a per-chunk
   `cublasCreate`/`cublasDestroy` (each an implicit device sync). Replaced
   with a size-keyed free-list scratch pool (`scratch_acquire`/`scratch_
   release`) and a lazily-created, reused `blas_` handle. Same Tegra
   VMM-churn anti-pattern already fixed for WavLM weights, never for
   Conformer scratch.

### Offline result (120 s / 66 chunks, `/tmp/wave_30s.bin`)

| stage | before | after |
|-------|--------|-------|
| seg   | 12450 ms | **9400 ms** (−24 %) |
| total | ~17.8 s | ~14.8 s |

Reproduced 3× (9590 / 9447 / 9355 ms). fp32 bit-eq PASS 28/28 — the scratch
pool hands back uninitialised buffers that consumers overwrite before read,
so the result is bit-equivalent to a fresh `cudaMalloc`.

`accuracy(tests/test.mp3, diarization): unchanged (bit-identical fp32 PASS 28/28)`

### Why offline understates the win

Offline the VMM map is clean, so alloc churn is cheap; the 24 % seg drop is
the *floor*. Live (WavLM-ECAPA + Silero VAD + ring buffers co-resident, map
fragmented) the same per-chunk churn was catastrophic for the WavLM weights
(~1268 s) — the Conformer scratch/handle removal attacks the identical
hazard, so the live gain should exceed the offline 24 %. Full live RTF
re-measure is deferred per the owner's instruction (iterate offline until
RTF is ideal, then one live gate).

## RTF push 2 — ResNet34 embedder: per-chunk backbone sharing + conv plan cache

A fresh nsys profile after the Conformer fix showed the **embed stage
(ResNet34 x-vector) is now the largest GPU consumer** — the obviously-ResNet34
kernels (cutlass tf32 fprop 13 % + r34_bn_relu 10.3 % + winograd 9.1 % +
nchwToNhwc 7.4 % + r34_add_relu 5.1 % + cutlass analytic 5.1 % + nhwcToNchw
4.0 %) sum to ~54 % of GPU time. Two bit-identical levers landed.

### 1. Backbone sharing (the big one): embed 5329 → 1382 ms (−74 %)

`get_embeddings` looped `for chunk: for speaker: embed(chunk, mask)` —
recomputing the **entire ResNet34 backbone S=4 times per chunk**, once per
speaker, when the backbone is a pure function of the chunk waveform (the
speaker mask only enters the pooling head). Split `embed()` into
`embed_backbone()` (fbank → stem → 16 blocks, stored in `d_backbone_`) and
`embed_pool()` (mask interp → stats pooling → seg_1 projection). The pipeline
now calls the backbone once per chunk and pools per speaker. Same ops, just
deduplicated → bit-identical, and the dominant conv cost drops by ~S×.

### 2. cuDNN conv plan cache

`conv2d_` created+destroyed 4 cuDNN descriptors and ran a
`cudnnGetConvolutionForwardAlgorithm_v7` heuristic on **every** conv of every
call. ResNet34's ~36 conv shapes are fixed once the chunk length is fixed, so
the plan (descriptors + chosen algo) is now cached by
`(C_in,C_out,H,W,K,stride,pad)`. Same algo selected → bit-identical; removes
the per-conv descriptor churn (helps live under a fragmented VMM map).

### Offline result (120 s / 66 chunks, all background processes killed)

| stage | before push 2 | after |
|-------|---------------|-------|
| seg   | ~6240 ms | ~6235 ms |
| embed | 5329 ms | **1382 ms** (−74 %) |
| total | 11583 ms | **7631 ms** (−34 %) |

fp32 bit-eq PASS 28/28 (end2end segs 28/28, labels match, max boundary diff
0.02 s).

`accuracy(tests/test.mp3, diarization): unchanged (bit-identical fp32 PASS 28/28)`

### Note on the earlier 9.4 s seg figure

The 9.4 s seg measured right after the Conformer commit was taken while
background `awaken`/`diarizen_live_score` processes contended for the GPU.
With everything killed, clean seg is ~6.2 s — the Conformer scratch-pool win
stands; the 9.4 s was contention, not regression.

## DiariZen clustering — agglomeration moved off CPU onto GPU (bit-identical)

`accuracy(tests/test.mp3, diarization): unchanged (bit-identical fp32 PASS 28/28; full-session output BYTE-IDENTICAL)`

### The CPU that ran "the whole time"

Thomas observed a CPU core pinned for the entire test run. The seg and embed
stages are already GPU-resident (cuDNN / cuBLAS), so the only sustained
*pure-CPU* compute left in `diarize()` was the **clustering** stage. An
env-gated sub-stage profiler (`DEUSRIDET_DIARIZEN_CLUSTER_PROF=1`, emits one
`[cluster-prof]` line) over the full 60-min session (C=2251 chunks, N=3894
leaves) pinned the culprit:

```
[cluster-prof] N=3894 K0=533 Kc=4 C=2251 S=4 |
  filter=20.3  ahc=40949.4  fea=305.8  vbx=6438.1  cent=1.4  soft=11.9  assign=1.1  total=47730.1 ms
```

The agglomerative centroid-linkage merge (`ahc`) was **40 949 ms = 86 %** of
the clustering wall and a single, uninterrupted CPU burn — exactly the core
that "ran the whole time". The merge is `n−1` dependent steps, but the two
heavy per-step operations are data-parallel: the global-minimum scan over the
active pair set (O(active²)) and the Lance-Williams centroid update
(O(active)), plus the one-shot pairwise distance (O(n²)).

### What shipped

`src/orator/diarizen_clustering_ahc.{cu,h}` — a GPU centroid-linkage merge:

- `pdist_kernel`: one thread per (i,j), **sequential fp64 accumulation** over
  the embedding dimension — keeps the CPU summation order, no reduction.
- `argmin_kernel` + `reduce_kernel`: block-reduce the active pair set with a
  **lexicographic (dist, i, j) comparator** that reproduces the CPU's
  "first strictly-smaller in row-major scan" tie-break bit-for-bit.
- `lw_kernel`: Lance-Williams centroid update mirroring `centroid_lw`'s exact
  fp64 op order.
- Host driver runs the serial `n−1` merge loop, recording the tree on the
  host (sub-ms); the fcluster DFS numbering and MD computation stay on CPU
  (tiny, serial). On any CUDA error it returns `false` and
  `agglomerative_()` falls back to the original CPU path verbatim.

### Result (full 60-min session, offline profile)

```
[cluster-prof] N=3894 K0=533 Kc=4 C=2251 S=4 |
  filter=20.0  ahc=3669.3  fea=308.5  vbx=6015.0  cent=1.4  soft=11.9  assign=1.1  total=10028.7 ms
```

| sub-stage | CPU | GPU | Δ |
|-----------|-----|-----|---|
| ahc | 40 949.4 ms | **3 669.3 ms** | **−91.0 %** |
| cluster total | 47 730.1 ms | **10 028.7 ms** | **−79.0 %** |
| diarize total | 369 879 ms | **332 468 ms** | **−10.1 %** |

**Bit-identity proven two ways:** (1) the 29-chunk fixture bit-eq harness
`RESULT: PASS` (segs 28/28, labels_match, `min_cos=0.999980`); (2) — stronger
— the full-session output over the real 60-min audio is **byte-identical**:
`cmp /tmp/out_full.bin /tmp/out_full2.bin → BYTE-IDENTICAL` (20196/20196 bytes).
So accuracy is provably unchanged at 93.6 %; only the CPU burn moved to GPU.

**Tegra memory note:** the merge allocates a transient pairwise-distance
buffer `dD` of `total² × 8 B` (≈ 485 MB at N=3894), freed at the end of each
`diarize()` (~once per 10-min finalize). Env-gated/lazy, not resident; scales

**New dominant cluster sub-stage:** with `ahc` off the CPU, **VBx
(6 015 ms, still CPU)** is now the largest clustering CPU consumer. Doc
`12-diarizen.md` risk #3 deferred VBx to CPU as "promote to GPU only if
profiling shows it matters" — it now matters, but VBx (PLDA + VB-HMM

## DiariZen `diarize()` sub-stage profile — the finalize is already GPU-bound

`accuracy(tests/test.mp3, diarization): unchanged (env-gated timers only, bit-identical)`

The recurring concern is "the CPU runs the whole time" — so before porting
anything else to the GPU we measured *where* the `diarize()` finalize actually
spends its wall time. Two new env-gated sub-stage profilers were added,
mirroring the existing `DEUSRIDET_DIARIZEN_CLUSTER_PROF=1` pattern:

- `DEUSRIDET_DIARIZEN_SEG_PROF=1` → `[seg-prof]` splits the segmentation stage
  into `fill` (host chunk copy) / `wavlm` (GPU encoder) / `conf` (GPU Conformer)

- `DEUSRIDET_DIARIZEN_EMB_PROF=1` → `[emb-prof]` splits the embedding stage into
  `backbone` (GPU ResNet34, once/chunk) / `pool` (GPU masked stats, S/chunk).

Both are pure `std::chrono` timers behind a `getenv` gate; off by default,
zero runtime cost, and bit-identical (fixture bit-eq `RESULT: PASS`, segs

```

[emb-prof]     C=2251 S=4       | backbone=10143.0  pool=36065.9 ms
[cluster-prof] N=3894 K0=533 Kc=4 ... vbx=6436.5 ... total=10453.1 ms
```

| where | ms | device | note |
|-------|----|--------|------|
| WavLM-pruned encoder | 261 417 | **GPU** | 24-layer transformer, 78 % of `diarize()` |
| Conformer head | 14 076 | **GPU** | batch=1/chunk, 4 % |
| ResNet34 backbone+pool | 46 209 | **GPU** | 14 % |

| host glue (fill+decode+post) | ~395 | CPU | one-shot bookkeeping, 0.1 % |

### Conclusion — no continuous-CPU hog remains in `diarize()`

The finalize is **already GPU-first compliant**. The seg stage (the 78 %
giant) is 99.9 % GPU transformer compute — its host side is only `fill`
271 ms + `decode` 72 ms (a sub-second one-shot copy + argmax, exactly the
"tiny serial glue" the GPU-first mandate permits on the CPU). embed and AHC
are GPU. The single remaining sustained CPU compute is **VBx EM = 6 436 ms**
(1.9 % of `diarize()`).

VBx stays on CPU **by deliberate decision**, not omission:

1. It is a **finalize-only burst** — `diarize()` runs once per session; the
   live RTF is already 0.19 and VBx contributes ~0.002 to it. A GPU port
   cannot move the feasibility gate.
2. It is **bit-identity-fragile**. VBx is a 20-iteration Bayesian-HMM EM with
   an ELBO convergence break; routing its two fp64 GEMMs through cuBLAS DGEMM
   would not reproduce the CPU's sequential FMA-contracted summation order, so
   a tiny rounding difference could shift convergence by one iteration and
   *silently* change cluster assignments — precisely the silent-accuracy-
   regression class the Constitution (rule #9) warns against. It would forfeit
   the cheap byte-identity gate and force a 40-min live-accuracy validation for
   a 6 s burst with no throughput or accuracy upside.

So the right call is to **stop here**: the "CPU runs the whole time"
observation is the CPU busy-waiting on GPU kernel launches/syncs during the
long WavLM forward, not host compute that can be relocated. The profilers are
kept env-gated as permanent diagnostics so any future regression is one
`getenv` away from being seen.

## P3c default-flip gate — LLM-loaded native verify, two blockers fixed

`accuracy(tests/test.mp3, diarization): 93.5% → 93.6%   (Δ = +0.1 pp)`

The P3c gate requires the native DiariZen path to hold ≥ 93.5 % live **with
the 27B LLM loaded** (`DEUSRIDET_TEST_WS_ENABLE_LLM=1`), because the
holdback worker only activates when an LLM is present to consume the
relabelled transcripts. That configuration had never produced an accuracy
line — the run crashed. Root-causing it exposed two independent bugs.

### Blocker 1 — periodic worker O(N²) re-diarise poisons the CUDA context

`DiarizenPeriodicWorker::run_one_pass_()` re-diarises the **entire**
accumulated session every 60 s. Cost grows O(N) per pass × N/period passes =
O(N²). The live log showed three timed passes at C=130 (16.8 s), C=514
(70 s), C=1165 (**211 s**) — a single late pass monopolised the shared GPU
for 3.5 minutes, starving the live perception pipeline (FRCRN enhancer +
Silero VAD + WavLM-ECAPA speaker-id). The audio ring buffer overflowed
91,612 times; FRCRN then hit an illegal memory access (a memory-pressure
fault surfacing at the first GPU sync), the whole CUDA context was poisoned,
and the final full-session diarize never ran — so no `speaker_diarize_final`
was broadcast and the score client hung. This is exactly the failure the old
IPC "P2-verify" row recorded ("worker re-extraction loop"), now precisely
identified: the worker only runs when the LLM is loaded, which is why all
four prior no-LLM gates were clean at RTF 0.19.

**Fix (A).** The timed cadence is now gated behind
`DEUSRIDET_DIARIZEN_PERIODIC=1` (default **OFF**). By default the worker only
diarises on an explicit `diarizen_trigger` or session-end `diarizen_finalize`
— no full-session re-diarise during streaming, no GPU monopolization, no
starvation, no context poison. Mid-conversation real-time relabel becomes
opt-in. The full re-diarise design is fundamentally incompatible with the
in-process native path on a shared GPU.

**Fix (D, hardening).** `FrcrnGpu::enhance()` (device path) gained the same
`if (n_samples > max_samples_) return 0;` boundary clamp that `enhance_host`
already had — an over-long chunk produces more STFT frames than the conv
buffers were sized for, overflowing cuDNN's ConvT2d → `BAD_PARAM` → illegal
access. Defense-in-depth; touches no forward math (bit-eq unchanged).

### Blocker 2 — LLM-loaded finalize broadcast schema mismatch

With the LLM loaded, `diarizen_finalize` routes through `worker->finalize()`
(not the native-direct path). The worker's broadcast used object-form
segments `{start,end,label}` and carried no `ok` field, while the live score
client requires `final.get("ok")` truthy **and** array-form segments
`[start,end,label]`. Every LLM-loaded finalize was therefore unscoreable
(`[diarize] FAILED: unknown`). Fixed by emitting `ok` + array-form segments +
`audio_sec`/`wall_sec` + `n_segments` while keeping `segment_count`/`pass`/
`origin_sec`/`changed_pending`. The WebUI panel already accepts both segment
forms, so it is unaffected; an empty-segments final now also broadcasts an
explicit error so no client hangs.

## Vires architecture A — thread a Background stream through DiariZen native path

`accuracy(tests/test.mp3, diarization): 93.6% → 93.6%   (Δ = 0.0 pp)`

Vires V1 (commit `e3ef92b`) shipped the compute-substrate allocator but no
consumer was routed through it yet — the native DiariZen forward path still
launched every kernel on the Tegra legacy default stream (stream 0), which is
a *global synchronisation barrier* that serialises against perception's
private streams. That is the structural half of the P3c GPU-monopoly.

Architecture **A** (explicit per-kernel stream threading, chosen over the
global `--default-stream per-thread` option B) threads a single
`cudaStream_t stream_` member — defaulting to `nullptr` (= default stream, a
provable no-op) — through every native sub-model:

- **ResNet34 embedder**, **Conformer head**, and **WavLM-pruned encoder** each
  gained `set_stream(cudaStream_t)` that stores the stream and binds any
  already-created cuBLAS / cuDNN handle (`cublasSetStream` / `cudnnSetStream`).
  Every raw `<<<grid,block>>>` became `<<<grid,block,0,stream_>>>`; hot-path
  `cudaMemcpy` became `cudaMemcpyAsync(...,stream_)`; `cudaDeviceSynchronize()`
  became `cudaStreamSynchronize(stream_)`; `cudaMemset` became
  `cudaMemsetAsync`. Free helpers that take only a cuBLAS handle
  (`clinear_`, `linear_`) read the stream straight off the bound handle via
  `cublasGetStream`, so their ~9 call sites each were untouched.
- `DiarizenSegmenter::set_stream` forwards to both sub-models;
  `DiarizenPipeline::load` registers a `"diarizen"` Vires **Background**
  consumer and binds its priority stream onto the segmenter + embedder.

The stream choice changes *scheduling priority only* — same kernels, same
launch order, same math — so the result is bit-identical: the P3a fixture
bit-eq stayed `PASS` (28/28 segments, `min_cos 0.999980`) and the live
accuracy is unchanged at 93.6 % (per-speaker 唐 0.939 / 徐 0.920 / 朱 0.835 /
石 0.971, 527/531 decided, coverage 0.992).

The point of the change is contention, not accuracy — and it landed: live
finalize wall dropped from **685 s → 359.6 s** (RTF 0.19 → 0.099) because the
Background priority stream no longer barriers against the live perception
streams. 0 CUDA errors, no FRCRN `BAD_PARAM`, native pipeline LOADED, HTTP
200 / WS 101. Boot log confirms `[vires] registered consumer #1 'diarizen'
[background] prio=0`.

## Vires — wire *all* GPU consumers (Foreground perception/prefill/decode)

`accuracy(tests/test.mp3, diarization): 93.5% → 93.6%   (Δ = +0.1 pp)`

With the first Background consumer proven (DiariZen, above), the invariant is
made permanent: **now and forever every GPU compute consumer registers with
Vires** instead of owning a raw private stream. Perception, prefill and decode
register as **Foreground** (priority −5, the greatest); refinement /
consolidation register as **Background** (priority 0). The wiring is uniform —
replace each `cudaStreamCreate(&stream_)` with
`register_consumer("<name>", Foreground); stream_ = Arbiter::stream(id)` in the
ctor/init and `unregister_consumer(id)` in the dtor:

- **Orator** — `speaker_encoder` (`orator_spk_encoder`) and the three
  `speaker_vector_store` instances (`orator_spk_store_{CamppDb,WLEcapaDb,DualDb}`).
- **Sensus / Auditus** — `speech_separator` (`auditus_separator`, stream passed
  into `MossFormer2::init`), `overlap_detector` (`auditus_overlap`, PyannoteSeg3
  inherits via `seg3_.init(path, stream)`), and `asr_engine` (`auditus_asr`,
  registered only when ASR is enabled).
- **Machina** — `InferenceState` now registers `machina_compute` + `machina_aux`
  Foreground (replacing its two private `cudaStreamCreate` calls); the streams
  stay graph-capturable (`cudaStreamNonBlocking` + priority) so CUDA-graph
  capture is unaffected. Registered only when an LLM is loaded.

These are scheduling-priority-only changes — same kernels, same launch order,
same math — so they are bit-identical: the P3a fixture bit-eq stayed `PASS`
(28/28 segments, `min_cos 0.999980`) and the live gate reproduced the afe9a15
baseline exactly (micro 0.936, macro 0.916, per-speaker 唐 0.939 / 徐 0.920 /
朱 0.835 / 石 0.971, 527/531 decided, coverage 0.992). Boot log of the no-LLM
no-ASR default confirms six consumers register —
`orator_spk_store_{CamppDb,WLEcapaDb,DualDb}` + `auditus_overlap` +
`orator_spk_encoder` as `[foreground] prio=-5`, and `diarizen` as
`[background] prio=0` — with HTTP 200 / WS 101 and 0 errors
(`machina_compute`/`machina_aux` + `auditus_asr` register only under their
respective gates).
