### Why the default is NOT flipped yet — throughput feasibility

The native `diarize()` is **single-chunk** (no batching): one WavLM-pruned
(24 transformer layers) + Conformer + ResNet34 forward per 1.6 s step, over
~2260 chunks. Measured cost: **0.87 s/chunk → 1943.6 s (RTF 0.54)** for the
60-min session. The shipped Python-IPC path runs the *same* finalize in
753.7 s (RTF 0.21) because the reference DiariZen stack batches at 32.

So the native path is accuracy-parity (slightly better) but **2.6× slower**
than what ships today. Per Prime Directive #9, accuracy decides *improvement*
but throughput gates *feasibility* — flipping the default now would be a
throughput regression. **Batching the WavLM/Conformer/ResNet34 forwards
(batch_size = 32, like the reference) is the gating perf task before the
default-flip.** The single-sequence CUDA forwards (`[C,T]`/`[T,C]` layouts,
no batch axis) make this a large, paced multi-file change; the 60 s-fixture
bit-equality must stay green throughout.

### Memory budget

When `DEUSRIDET_DIARIZEN_NATIVE=1`, WavLM-pruned (120.85 MB) + Conformer
(11.63 MB) + ResNet34 (16 blocks) + PLDA (xdim 256, pdim 128) become
process-resident instead of a Python subprocess. Default-off keeps current
residency (Prime Directive #5).

## UPDATE — throughput feasibility gate CLEARED (native beats Python live)

The "2.6× slower" verdict above was **wrong about the cause**. It was not a
batching deficit — it was Tegra `cudaMalloc`/`cudaFree` churn under a
fragmented live VMM map. Closing it required *no* batching, only the same
persistent-weight-cache discipline already applied to WavLM.

Commits this update (all bit-equality-preserving, `internal-check-only`,
accuracy unchanged at 93.7 %):

- `75a92e4` persistent fp32 weight cache in WavLM-pruned encoder
- `cdea087` persistent scratch pool in WavLM-pruned forward
- `c5a800a` cuBLAS batched GEMM for WavLM attention scores/context
- `7bee0c5` cuBLAS batched GEMM for Conformer MHSA scores/context
- `fd79f9c` coalesce channel LayerNorm in WavLM CNN frontend
- `7dd64d7` persistent fp32 weight cache in Conformer head + diarize stage timing

### The kernel/allocator diagnosis

`nsys` showed three hand-rolled kernels doing uncoalesced strided global
work (WavLM `attn_scores_kernel` 42.7 %, Conformer `mhsa_scores_kernel`
13.1 %, `layer_norm_channels_kernel` 20.2 %); all replaced with
`cublasSgemmStridedBatched` / coalesced rewrites. But the decisive lever was
the **per-chunk weight allocation churn**: both WavLM (24 layers) and the
Conformer head (4 layers + classifier) re-converted every fp16 weight to a
fresh fp32 device buffer (`cudaMalloc` + `half_to_float` + `cudaFree`) on
*every* chunk — ~324 K `cudaMalloc`/`cudaFree` calls per 60-min session.

On Tegra every `cudaMalloc`/`cudaFree` walks the global VMM map. **Offline**
(clean, small map) this churn cost only ~18 s. **Live** — with WavLM-ECAPA,
Silero VAD and the ring buffers co-resident, the global VMM map is large and
fragmented — the *same* churn cost ~1268 s. This is exactly the hazard the
`diarizen_wavlm_pruned.h` comment warns about; PyTorch never pays it because
of its caching allocator. The fix is a persistent device-resident fp32 cache
keyed by tensor name (`weight_f32()`), converting once at first use.

## RTF push — TF32, WavLM dense batching, Conformer scratch pool (offline, bit-identical)

After the live feasibility gate cleared at RTF 0.190, the owner was still
dissatisfied: "this model isn't large — it's that our CUDA kernels aren't
efficient." A profiling-driven offline push followed. Each lever is
bit-identical (fp32 bit-eq harness PASS 28/28), so accuracy is unchanged.

### Levers landed

1. **TF32 tensor-core math** (env-gated `DEUSRIDET_DIARIZEN_TF32`, default ON):
   route the dense GEMMs through Ampere tensor cores via
   `CUBLAS_TF32_TENSOR_OP_MATH`. fp32 bit-eq is preserved by setting `=0`.
2. **WavLM dense-linear batching**: stack `B` chunks into fused `[B*T, H]`
   GEMMs (`debug_lnorm_tail_batch` + B-aware `run_encoder_layer_`). Offline
   seg 13250 → 12450 ms. **Batch-size invariant** (B=8/16/33/66 all ~12.5 s)
   — proof the WavLM encoder *compute* is not the seg bottleneck.
3. **Conformer scratch pool + cached cublas handle**: the real seg-stage
   drain was the Conformer head's per-chunk `cudaMalloc`/`cudaFree` (~7
   buffers × ffn/mha/conv × 4 layers × 66 chunks) plus a per-chunk
   `cublasCreate`/`cublasDestroy` (each an implicit device sync). Replaced
   with a size-keyed free-list scratch pool (`scratch_acquire`/`scratch_
   release`) and a lazily-created, reused `blas_` handle. Same Tegra
   VMM-churn anti-pattern already fixed for WavLM weights, never for
   Conformer scratch.

### Offline result (120 s / 66 chunks, `/tmp/wave_30s.bin`)

| stage | before | after |
|-------|--------|-------|
| seg   | 12450 ms | **9400 ms** (−24 %) |
| total | ~17.8 s | ~14.8 s |

Reproduced 3× (9590 / 9447 / 9355 ms). fp32 bit-eq PASS 28/28 — the scratch
pool hands back uninitialised buffers that consumers overwrite before read,
so the result is bit-equivalent to a fresh `cudaMalloc`.

`accuracy(tests/test.mp3, diarization): unchanged (bit-identical fp32 PASS 28/28)`

### Why offline understates the win

Offline the VMM map is clean, so alloc churn is cheap; the 24 % seg drop is
the *floor*. Live (WavLM-ECAPA + Silero VAD + ring buffers co-resident, map
fragmented) the same per-chunk churn was catastrophic for the WavLM weights
(~1268 s) — the Conformer scratch/handle removal attacks the identical
hazard, so the live gain should exceed the offline 24 %. Full live RTF
re-measure is deferred per the owner's instruction (iterate offline until
RTF is ideal, then one live gate).

## RTF push 2 — ResNet34 embedder: per-chunk backbone sharing + conv plan cache

A fresh nsys profile after the Conformer fix showed the **embed stage
(ResNet34 x-vector) is now the largest GPU consumer** — the obviously-ResNet34
kernels (cutlass tf32 fprop 13 % + r34_bn_relu 10.3 % + winograd 9.1 % +
nchwToNhwc 7.4 % + r34_add_relu 5.1 % + cutlass analytic 5.1 % + nhwcToNchw
4.0 %) sum to ~54 % of GPU time. Two bit-identical levers landed.

### 1. Backbone sharing (the big one): embed 5329 → 1382 ms (−74 %)

`get_embeddings` looped `for chunk: for speaker: embed(chunk, mask)` —
recomputing the **entire ResNet34 backbone S=4 times per chunk**, once per
speaker, when the backbone is a pure function of the chunk waveform (the
speaker mask only enters the pooling head). Split `embed()` into
`embed_backbone()` (fbank → stem → 16 blocks, stored in `d_backbone_`) and
`embed_pool()` (mask interp → stats pooling → seg_1 projection). The pipeline
now calls the backbone once per chunk and pools per speaker. Same ops, just
deduplicated → bit-identical, and the dominant conv cost drops by ~S×.

### 2. cuDNN conv plan cache

`conv2d_` created+destroyed 4 cuDNN descriptors and ran a
`cudnnGetConvolutionForwardAlgorithm_v7` heuristic on **every** conv of every
call. ResNet34's ~36 conv shapes are fixed once the chunk length is fixed, so
the plan (descriptors + chosen algo) is now cached by
`(C_in,C_out,H,W,K,stride,pad)`. Same algo selected → bit-identical; removes
the per-conv descriptor churn (helps live under a fragmented VMM map).

### Offline result (120 s / 66 chunks, all background processes killed)

| stage | before push 2 | after |
|-------|---------------|-------|
| seg   | ~6240 ms | ~6235 ms |
| embed | 5329 ms | **1382 ms** (−74 %) |
| total | 11583 ms | **7631 ms** (−34 %) |

fp32 bit-eq PASS 28/28 (end2end segs 28/28, labels match, max boundary diff
0.02 s).

`accuracy(tests/test.mp3, diarization): unchanged (bit-identical fp32 PASS 28/28)`

### Note on the earlier 9.4 s seg figure

The 9.4 s seg measured right after the Conformer commit was taken while
background `awaken`/`diarizen_live_score` processes contended for the GPU.
With everything killed, clean seg is ~6.2 s — the Conformer scratch-pool win
stands; the 9.4 s was contention, not regression.
