# DEVLOG 2026-06-01

## Vires — broaden Foreground heartbeats to machina prefill/decode + ASR

Commit this session:

- `738fc66` feat(vires): broaden Foreground heartbeats to machina + ASR

`accuracy(tests/test.mp3, diarization): 93.5% → 93.6%   (Δ = +0.1 pp)`

### What shipped

Until now only `orator_spk_encoder` emitted Vires `note_submit`
heartbeats, so the Foreground-yield arbitration — and the WebUI
vires-panel — only reflected speaker-encoder load. Every other
Foreground GPU consumer registered with the Arbiter but never reported
activity, leaving its `submitted` counter pinned at zero and its load
invisible to `background_should_yield()`.

This change adds the same one-line, bit-identical heartbeat to every
Foreground consumer that owns a compute stream:

- machina prefill (`forward_prefill`) → `state.vires_compute_id`
- machina decode (`forward_one_token` / `forward_one_token_sampled`) →
  `state.vires_compute_id`
- auditus ASR encoder (`ASREngine::transcribe`) → `vires_id_`

Each is a single `vires::Arbiter::instance().note_submit(id)` issued
right after the existing `cudaStreamSynchronize`. It changes no kernel,
no math, and no execution order — it only bumps the per-consumer
`submitted` counter and refreshes the `last_foreground_submit_us_`
timestamp that the Background DiariZen path reads to decide whether to
yield. `note_submit` takes a single short-held mutex with no nested
locks or callbacks, so there is no deadlock or reordering risk.

The net effect: `background_should_yield()` now honours true Foreground
load across all active consumers (not just the speaker encoder), and the
WebUI vires-panel shows real `submitted` counts for prefill, decode, and
ASR instead of a flat zero.

The heartbeats are bit-identical to the GPU math by construction, so

diarizen gate does not trigger LLM decode).

## Vires V3 — Glymphatic clearance (non-LLM scratch reclamation)

V1 stored each consumer's `reclaim_cb` but never called it; V2 added
back-pressure + telemetry. V3 closes the loop: when a **non-LLM** GPU
pass completes, Vires invokes that consumer's reclaim callback to hand
back the transient scratch it was lent — the "glymphatic clearance" of
compute by-products (RFC 13). No LLM allocation is touched; LLM waste
remains Memoria's charge.

### What changed (scheduling/lifetime only — bit-identical math)

- `ConsumerStat` gains a monotonic `reclaimed` counter (alongside
  `submitted`), surfaced in the `vires_compute_snapshot` WS message and
  a new **Reclaimed** column in the WebUI `vires-panel`.
- New facade method `Arbiter::note_pass_complete(id)`. It copies the
  consumer's `reclaim_cb` out **under** the lock, bumps `reclaimed`,
  then releases the lock and invokes the callback **outside** it —
  preserving the V1/V2 invariant that no callback ever runs under the
  Vires mutex (no nested-lock / deadlock risk). No-op for an unknown id
  or a consumer with no callback.
- The Background `diarizen` consumer registers a reclaim callback
  (`segmenter.release_scratch()`) and calls `note_pass_complete` at the
  end of every `DiarizenPipeline::diarize`. `release_scratch()` frees
  **only** the transient forward by-products — the WavLM-pruned encoder's
  size-keyed scratch free-list + its on-demand cuDNN conv workspace, and
  the Conformer head's scratch free-list. Persistent state (weight arena,
  fp32 weight cache, cuBLAS/cuDNN handles, `loaded_`) is kept, so the
  model stays ready and re-grows its pool lazily on the next pass. Those
  buffers are always fully overwritten before being read, so a clear is
  bit-equivalent to fresh allocation. The ResNet34 embedder owns no
  scratch pool, so it has nothing to reclaim.
